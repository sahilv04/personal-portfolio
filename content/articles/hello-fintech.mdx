# Why I Build for Fintech

Most software fails quietly. A 500 here, a stale cache there — the user reloads, the page works, the world moves on. **Fintech doesn't get that.** When a settlement misfires, money lands in the wrong account; when a flow times out, a trade desk is exposed. The cost of being wrong is concrete, denominated, and audited.

That asymmetry is what makes the engineering interesting.

## What "good" looks like

- **Idempotency by default.** Every operation runs as if it might be retried, because it will be.
- **State machines, not procedures.** Settlement isn't a function call — it's a graph of states with clear transitions, each one auditable.
- **Reconciliation as a first-class feature.** If your system can't prove its own balances against an external source of truth, it isn't done.

```ts
type SettlementState =
  | { status: "proposed"; tradeId: string }
  | { status: "matched"; tradeId: string; counterpartyId: string }
  | { status: "settled"; tradeId: string; ledgerTxId: string }
  | { status: "failed"; tradeId: string; reason: string };
```

A type like this is cheap to write and expensive to skip. It forces every consumer to handle every state. Compiler nags become production guarantees.
